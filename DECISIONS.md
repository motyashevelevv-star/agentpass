# Архитектурные решения

1. **Детерминированные правила вместо LLM.** Финансовый verdict полностью определяется валидированным intent, актуальным мандатом и записанными резервами. Нейросеть может появиться позже только перед созданием intent.
2. **PostgreSQL как источник истины.** Row locks и транзакции дают сериализацию бюджета на нескольких API-процессах. Redis для этой версии не нужен. Тесты конкуренции работают с PostgreSQL, без SQLite и process mutex.
3. **Общий порядок блокировок.** Advisory lock идемпотентности → agent → mandate → intent → approval/reservation. Отзыв и исполнение используют те же блокировки. API-ключ сериализует собственные запросы с отзывом; ограничение производительности документировано.
4. **Целые суммы.** API использует копейки для RUB. UI переводит рубли в целые копейки только на границе ввода. FX и конвертация валют отсутствуют.
5. **ASK без резерва.** Ожидающие запросы не блокируют бюджет. Подтверждение может быть отклонено, если бюджет потрачен другими запросами. UI объясняет эту семантику.
6. **Разрешение отдельно от исполнения.** APPROVE создаёт краткоживущий резерв; execute создаёт симулированный чек. Никаких реальных денег, счетов или реквизитов.
7. **Безопасное изменение правил.** ASK проверяется по текущей версии. Уже выданное разрешение инвалидируется при изменении версии перед исполнением, даже если новая версия выглядит менее строгой. Агент должен создать новый intent.
8. **Сессии в БД вместо JWT.** Отзыв централизован, токены хешируются; cookie HttpOnly/SameSite, CSRF и Origin проверяются сервером. Только локальный sandbox допускает insecure cookie.
9. **Ключ агента не может подтверждать свои покупки.** SDK использует agent-bound key. Управление мандатами, подтверждениями и аккаунтом требует пользовательской сессии.
10. **Outbox в бизнес-транзакции.** Не теряется событие между решением и постановкой доставки. At-least-once требует дедупликации у получателя. MVP держит DB lock до сетевого ответа; будущий lease worker снимет это ограничение.
11. **Локальный receiver с узким исключением.** Публичные webhooks только HTTPS и public IP. В sandbox разрешён один конфигурационный HTTP URL собственного API для полноценного офлайн-демо доставки; вне sandbox исключения нет.
12. **Append-only audit с оговоркой.** SQL trigger блокирует UPDATE/DELETE обычными statements. DB owner может отключить trigger или выполнить TRUNCATE; это не WORM и не защита от администратора БД.
13. **Frontend только с API.** TanStack Query ведёт серверное состояние, формы RHF/Zod выполняют раннюю валидацию; окончательные проверки всегда backend. Recharts строит графики из сохранённых операций.
14. **Простой русский MVP.** Доменные коды независимы от языка, есть shared locale boundary. Полного перевода UI на английский нет; это честная граница версии.
15. **Локальное инфраструктурное приложение.** Пользователь запросил FastAPI/PostgreSQL/Docker, поэтому используется этот стек и воспроизводимый checkout. Публикация на платформу статических Sites не заменяет backend и в задачу не входит.

## 2026-10-30 — усиление границы исполнения

- Сохранён REST v1: decision=ASK и sandbox execute остаются; decision_kind=ASK_USER и execution endpoints добавлены без замены старых клиентов.
- Signed grant HMAC используется внутри AgentPass между доверенными компонентами; это capability, не банковская цифровая подпись. Asymmetric verifier/HSM потребуют отдельного соглашения.
- Provider I/O вынесен из финансовой DB-транзакции в durable outbox с lease fencing. Unknown консервативно держит inflight во всех бюджетных окнах до сверки.
- Локальный simulator имеет отдельный durable journal. Для внешнего провайдера без lookup по idempotency key запрещено слепое пересоздание после неопределённого create.
- ЮKassa adapter выбран для документированного TEST redirect checkout. Не трактуется как банковское API или autonomous debit. Реальное соединение NOT VERIFIED.
- TOTP/step-up реализованы локально без внешнего сервиса. Enterprise OIDC ограничен offline validator; не выдаём его за готовый SSO.
- Composite financial FKs добавлены одной новой миграцией. RLS не включён без согласованной модели runtime roles/tenant context; это открытая задача security review.
- Pilot configuration fail-closed и runtime DB role checks сознательно исключают использование стандартного sandbox Compose как внешнего pilot deployment.
